# Контракт CHiO (`chio-v1`)

Статус: спецификация P15; реализация и проверки отмечаются в `reports/P15.md`.
Наличие этого документа не означает готовность ночного обучения.
Источники: требования P15 и [LastOrder-Dota2](https://github.com/bilibili/LastOrder-Dota2):
`agents/dota_agent.py`, `model/action_mask.py`, `model/utils.py`,
`gym_env/feature_processors/features_v0/features.py`, `gym_env/feature_processors/enums.py`.
При расхождении с LastOrder приоритет имеют требования P15 и измерения текущей Dota.

## Версия и совместимость

- Единственный новый профиль: `chio-v1`; отдельное окружение на основе 005.
- `ggd-v2/v3/v4`, 003/004/005, учителя v9/v10 и старые веса сохраняют свой контракт.
- Изменения физики разрешены только для `MOVE_DIRECT` в новом окружении.
- Урон, агро, касты, башни, крипы и поиск пути остаются прежними.
- Активы нового окружения копируются из 005; SHA-256 каждой таблицы и файла проверяется.
- Матч заканчивается первой смертью или потерей центральной T1; на 600 с — сравнение LH.
- Уточнение пользователя 06.11.2026: CHiO заканчивается сразу и при смерти в pregame.
  Старые профили сохраняют ожидание 0:00 после смерти в pregame, как в 005.

## Часы, исполнение и память

- 30 тиков/с; решение через 6 тиков (5 Гц), включая учителя и обоих соперников.
- При наблюдении тика `t`: due=`t+6`, исполнение=`due+1=t+7`.
- Старые профили допускают только decision_ticks=4; новые пары профиль/окружение проверяются явно.
- LSTM 256 обнуляется каждые 128 решений (25.6 с), при смерти и смене эпизода.
- Наблюдения в записи/rollout — FP16; вход вычисления — FP32, как у ZOg.
- Все длительности в секундах вычисляются из фактического числа тиков; рассинхронизация,
  фазовые счётчики и отчёты не должны сохранять множитель 4/30 для CHiO.

## Действия и условные головы

| ID | Тип | Дополнительная голова | Команда симулятора / Dota |
|---:|---|---|---|
|0|MOVE|направление 0..35|MOVE_DIRECT / серверный MOVE_TO_DIRECTION (28)|
|1|STOP|нет|STOP / Action_ClearActions(true)|
|2|ATTACK_ENEMY_CREEP|внимание по вражеским линейным крипам|ATTACK / Action_AttackUnit|
|3|DENY|внимание по своим крипам, HP≤50%|ATTACK / Action_AttackUnit|
|4|ATTACK_HERO|нет|видимый вражеский SF|
|5|ATTACK_TOWER|нет|видимая живая вражеская центральная T1|
|6|RAZE_NEAR|нет|койл 1|
|7|RAZE_MID|нет|койл 2|
|8|RAZE_FAR|нет|койл 3|
|9|REQUIEM|нет|ульта|
|10|USE_FLASK|нет|Flask на себя|
|11|USE_MANGO|нет|Mango на себя|
|12|EAT_TREE|нет|Tango на ближайшее живое дерево|

MOVE: абсолютный угол `k*10°`, 0° вдоль +x, против часовой стрелки.
Точка `observed_position + 2000*(cos(angle),sin(angle))`, x/y ограничены границами карты.
Приказ повторяется на каждом решении; расстояние не выбирается, маски направлений нет.
Уточнение пользователя 06.11.2026 после измерений: сохраняется движение без обхода,
эталон — `DOTA_UNIT_ORDER_MOVE_TO_DIRECTION` (28). `Action_MoveDirectly` в установленной
Dota обходит юнитов и меняет угол; он НЕ является исполнителем этого контракта.
Будущей Dota-интеграции нужен серверный мост для приказа 28.
Нет CONTINUE, HOLD, TP, Clarity, Stick, Faerie Fire, вардов и головы покупок.

Маски целей требуют живую видимую сущность и правильную команду/категорию;
пустое множество целей закрывает соответствующий тип. Повтор атаки той же сущности
и поколения не сбрасывает замах. Смена цели/типа следует действующим правилам симулятора.
Во время собственного каста от принятого приказа до срабатывания разрешены только STOP
и этот же скилл. Продолжение не требует заново доступных маны/CD и не перезапускает каст.
Если повторный приказ в Dota перезапускает каст, Dota-исполнитель подавляет такой повтор.
Маска обязана учитывать команду в очереди, чтобы 7 тиков задержки не открывали окно отмены
посторонним действием до появления каста в состоянии. STOP остаётся явной отменой.
Предмет: наличие в активном инвентаре и готовность; Flask дополнительно закрыт при его лечении.
EAT_TREE детерминированно выбирает ближайшее живое дерево; равенство расстояний — стабильный ID.

## Общая экономика

Wraith Band выдаётся режимом; один Tango покупается в pregame. TP не используется.
Один скрипт одинаков для CHiO, переведённого учителя и моделей-соперников CHiO.
Покупки v10 отключены только в режиме CHiO; бой учителя не меняется.
Прокачка и курьер сохраняют существующие правила.

`missing_hp=max_hp-hp`, `remaining_heal` — ещё не полученное активное лечение.
В таблицах 005 Flask даёт 30 HP/с ×13 с; Tango — 7 HP/с ×16 с.
Закупки считают остаток по этим неизменным таблицам. В штрафе сбитого Flask ниже
используется отдельно заданная пользователем оценка 50 HP/с; это не изменение регенерации.
Одна начальная покупка Tango содержит 3 заряда. Формулы используют число зарядов.
Числа Flask/Mango/Tango для закупки должны учитывать находящиеся в доставке предметы,
чтобы период опроса не создавал повторные заявки; семантика фиксируется тестами.

- `max_flask=2` до уровня 5, иначе 3.
- `need_flask = (Flask<1 && Tango==0) ||
  (Flask<max_flask && missing_hp>400*Flask+112*Tango+remaining_heal-100)`.
- `min_mana=min(max_mana, level<5 ? 360 : 450)`; `max_mango=level<5 ? 3 : 4`.
- `need_mango=(missing_hp<100 || !need_flask) &&
  min_mana>110*Mango+mana && Mango<max_mango`.
- Приоритет Flask, затем Mango, затем Boots и Bracer по `next_permanent`,
  причём постоянные предметы покупаются только когда оба расходника не нужны.

## Наблюдения и честность Bot API

Основа — ggd-v4 с честными таймингами P06, наблюдаемыми кастами P07 и oracle=false.
Обобщённые баффы не добавляются. Предметы у обоих героев: Wraith Band, Boots, Bracer,
Flask, Mango, Tango; TP/Clarity удаляются из входа CHiO.
Невидимые враги не читаются из точного состояния для признаков.

| Новый признак | Симулятор | Будущая Dota: конкретные функции и ограничения |
|---|---|---|
|HP, текущее и 11 прошлых решений, каждый герой/крип/башня|кольцевой буфер hp/max по entity ID+generation, обновление один раз за решение|IsAlive, CanBeSeen, GetHealth, GetMaxHealth; история по устойчивому handle/entity identity, не по месту в отсортированном списке|
|Known для каждой из 12 долей|нет видимости/юнит ещё не наблюдался/поколение сменилось → 0|CanBeSeen; при недоступном handle чтение запрещено; пропуск хранится как unknown, не перенос последнего HP|
|В моём near/mid/far койле, каждый юнит|расстояние от центра own_pos+own_facing*range ≤ radius, по таблицам spells|GetLocation, GetFacing; own GetAbilityByName, GetSpecialValueInt для shadowraze_range/radius; значения таблиц сверяются: 200/450/700, радиус 250|
|В радиусе моей атаки|геометрическое расстояние с принятой симулятором семантикой hull|GetAttackRange, GetLocation, GetBoundingRadius; hull/radius нужно сверить с текущим API, недоступное не подменять oracle|
|Угол на юнит относительно моего взгляда|wrap(atan2(dy,dx)-own_facing), единая шкала|GetLocation, GetFacing; нулевая дистанция имеет детерминированное значение|
|Я в near/mid/far койле видимого врага|та же геометрия, позиция и взгляд только видимого врага|CanBeSeen, GetLocation, GetFacing; враг скрыт → known=0; кулдаун врага не используется|
|Предыдущий тип CHiO|последняя выданная метка 0..12, включая STOP|локальная память исполнителя, не GetCurrentActionType (его enum иной)|
|Предыдущее направление|0..35 только для MOVE, иначе masked/0|локальная память исполнителя|
|Предыдущий тип цели|нет / вражеский крип / свой крип / герой / башня / дерево|локальная память исполнителя|
|Мой каст и его скилл|принятая очередь плюс CAST/CAST_END|локальная очередь; IsCastingAbility, IsUsingAbility, GetCurrentActiveAbility:GetName; завершение подтверждается API|

Известная история сохраняется при временной потере видимости, но новые скрытые отсчёты
имеют known=0. Данные умершего/переиспользованного юнита не переходят новому.
Криповые строки используют стабильное соответствие ID+generation при сортировке внимания.

## Модель и обучение

Размер и кодировщики ZOg: кодировщики юнитов, CNN карты, LSTM 256, value head.
Новые policy heads: 13 типов, 36 направлений, два внимания по крипам.
И в PyTorch, и в Burn одна нумерация полей/голов, веса экспортируются с версией контракта.
`log_prob = log p(type) + I(MOVE)*log p(direction)
 + I(ATTACK_ENEMY_CREEP)*log p(enemy_target) + I(DENY)*log p(ally_target)`.
Только использованные головы участвуют в NLL, PPO ratio, entropy и KL.
Паритет: 128 последовательных шагов с одной памятью, сравнение всех logits,
условного log-prob и value; проверка экспорта и обратного импорта.

## Награда `lastorder-fb-v1`

Точное состояние обоих героев используется только для награды/метаданных критика.
`f(h)=h+1-(1-h)^4`, `g(h)=h+1-(1-h)^3`, h — доля текущего максимума.
На каждом переходе решений:

| Компонент | Вклад |
|---|---|
|Опыт|0.002 * прирост суммарного опыта|
|Полученное золото|0.006 * прирост накопленного полученного золота, включая пассивное; покупки/потеря золота не вычитаются|
|Мана|0.5 * Δ(mana/max_mana)|
|HP|Δf(h)|
|LH|-0.12 * ΔLH|
|Deny|0.1 * Δdeny|
|Убийство героя|1.5 * Δkills|
|Своя смерть|-3 * Δdeaths|
|Своя T1|1.5 * Δg(tower_hp/tower_max)|
|Flask / Mango / Tango|-0.3 / -0.1 / -0.1 за подтверждённое использование|
|Сбитый Flask|max(f(h_after)-f(min(1,(hp_before+50*remaining_seconds)/max_hp_before)),-0.4), только прекращение от урона при неполном HP|
|Исход терминального шага|+5 / -5 / 0, ровно один раз|

С 360 игровых секунд компоненты кроме kill/death умножаются на 0.6;
терминальная добавка ±5 применяется отдельно и остаётся ±5.
`zero_sum=true` по умолчанию: из своей награды вычитаются все симметричные компоненты
врага, кроме его kill/death/outcome. `zero_sum=false` исключает это вычитание.
Каждая собственная и вычтенная компонента логируется отдельно.
gamma=0.997, GAE lambda=0.95; pregame имеет тот же шаг и участвует в обучении.

Запись каждого решения/перехода для ОБОИХ героев: gold_total_received, gold_current,
xp_total, hp/max, mana/max, своя и чужая T1 hp/max, LH, deny, kills, deaths,
накопленные использования Flask/Mango/Tango, оставшееся Flask-лечение, cast_active,
cast_skill, game_tick, terminal, outcome, reason. Начальный и следующий снимки должны
позволять пересчитать все компоненты, включая прекращение Flask от урона.
Нужен явный флаг причины прекращения Flask, чтобы не спутать урон, полное HP и истечение.
Пересчёт из записи сравнивается с online reward на каждом переходе, включая terminal.

## Перевод учителя v10

- MOVE к точке дальше 75: ближайшее направление из 36; на границе полубина —
  детерминированное округление; на расстоянии ≤75 — STOP.
- CONTINUE: повтор действующего приказа, цели и поколения; движение к действующей
  точке, активный каст → тот же скилл; нет приказа/точка достигнута → STOP.
- Атака вражеского линейного крипа / своего / героя / T1 → соответствующий тип.
  Неподдерживаемая/скрытая/невалидная цель → STOP с диагностическим счётчиком.
- STOP, койлы, ульта переносятся; Flask/Mango/Tango → соответствующий тип.
  Неподдерживаемые предметы не исполняются и учитываются отдельным счётчиком.
- Метка и исполнение создаются из одного результата; память учителя синхронизируется
  с исполненным действием по правилам teacher_dagger.
- Экономика из общего скрипта, не из головы/решения учителя.

## Приёмочные проверки

1. По 20+ Dota/симулятор повторов open, 90°, 180°, tree, edge, slope, ally creep,
   встречная волна, enemy hero; полные позиции по тикам, среднее/max отклонение,
   остановка, скольжение. Отдельно проверяется валидность начального положения/взгляда.
2. Все пути clock=6, offset=6/due+1, reset128/death, FP16; legacy побитово.
3. 13/13 переводов, все маски, same_cast, STOP cancellation, повторы атак всех типов.
4. Экономические пороги, запас/доставка, уровень 4→5, полный инвентарь/недостаток золота.
5. Каждый новый признак, туман, история/смерть/поколение, поворот, границы зон.
6. Экспорт/импорт, 128 шагов PyTorch/Burn, градиенты только использованных голов.
7. Каждый reward-компонент, знаки, 360с, zero-sum on/off, причины terminal, Flask;
   offline/online совпадают.
8. По 200 матчей: исходный v10×v10/005, CHiO v10×v10, CHiO v10×v9;
   seed20261103, farm ≥90% исходного, смерти ≤120%; максимум две итерации исправлений.
9. collect-teacher 8 матчей, imitation 50 конечных шагов, 100% меток под маской;
   готовые проверенные конфиги всех ночных этапов.

## Будущий Dota исполнитель

Для полноценной игры нужны Lua-исполнитель и серверный мост к MOVE_TO_DIRECTION (28),
очередь t+7 и частота 6, маска/продолжение/отмена каста, общий скрипт экономики,
история HP и признаки из таблицы, версия входов CHiO, CPU-инференс новых голов,
reset128/death и запись ACK. Диагностический исполнитель P15 не заменяет эту интеграцию.
